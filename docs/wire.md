# poler-wire v1 — спецификация транспорта POLER Mesh

> Заменяет туннели (localhost.run / cloudflared / ngrok / Tailscale) собственным
> каналом: **ноль входящих портов на машине владельца, ноль сторонних сервисов**.
> Релей — тупой слепой маршрутизатор на вашем VPS. Весь код — свой, Rust, std-треды.
> Из зависимостей только чистые криптопримитивы RustCrypto.

```
[удалённый агент]                        [ваш VPS]                    [ваш ПК]
GLM / Gemini / curl            HTTP POST /mcp*     poler-relay    raw TCP, исходящее
                                                ┌──────────────┐
                                                │  poler-relay │◄──── poler-mesh --mcp-link
                                                │ (слепой хаб) │────► (Hub: git+engine+…)
                                                └──────────────┘      держит соединение,
                                                                      реконнект с бэкоффом
```

Направление соединения — ключевое отличие от туннелей: **машина владельца сама
подключается наружу** (NAT неважен, входящих портов нет), а агент стучит в релей
обычным HTTP. Если релей слушает 443, для DPI это просто «бинарный трафик» —
содержимое зашифровано нами (см. §4), TLS не нужен.

## 1. Топология и роли

| Роль | Кто | Ключи |
|---|---|---|
| **link-клиент** | `poler-mesh --mcp-link` на ПК владельца | Ed25519 identity (подпись) + X25519 static (получение) |
| **relay** | `poler-relay` на VPS | Ed25519 identity (подпись HELLO_ACK) |
| **агент (sealed)** | скрипт `poler_agent.py` / любой, умеющий крипту | Ed25519 identity |
| **агент (plain)** | curl с Bearer-токеном | ничего — только токен |

Релей хранит только публичные ключи клиентов/агентов (конфиг) и **не имеет
никаких секретов для расшифровки трафика** (кроме собственного identity).

## 2. Кадр (client-leg, голый TCP)

Внешнее кадрирование — length-prefixed, всё big-endian:

```
┌──────────┬──────┬────────┬───────┬──────┬──────┬─────────────┐
│ len: u32 │ type │ cmd_id │ nonce │ time │ seq  │ ciphertext  │
│          │ u8   │  u64   │  u64  │ u64  │ u64  │ (переменная)│
└──────────┴──────┴────────┴───────┴──────┴──────┴─────────────┘
   len = длина всего после поля len. ciphertext = AEAD (вкл. 16 байт tag).
```

| type | имя | payload | направление |
|---|---|---|---|
| 0x01 | HELLO | JSON, не шифруется | C→R |
| 0x07 | HELLO_ACK | JSON, не шифруется | R→C |
| 0x02 | EXEC | JSON (§5) | R→C |
| 0x03 | RESULT | JSON (§5) | C→R |
| 0x04 | PING | `{"t":ms}` | оба |
| 0x05 | PONG | `{"t":ms,"rtt":…}` | оба |
| 0x06 | ERROR | `{"code":…,"message":…}` | оба |

`cmd_id` — идемпотентность (§6), `nonce` — анти-replay (§6), `time` — unixtime,
допуск ±300 c, `seq` — монотонный счётчик направления, входит в AEAD-nonce.
HELLO/HELLO_ACK передаются с нулевыми cmd_id/nonce/time/seq и открытым JSON.

Потолки: кадр ≤ 16 МБ; простой на client-leg ≤ 90 c (клиент пингует каждые 25 c).

## 3. Handshake (client-leg)

```
C→R  HELLO  {"v":1,"client_id":"main","eph":"<b64 X25519 eph pub>",
             "time":T,"nonce":N,"sig":"<b64>"}
      sig = Ed25519(client identity) над
            "poler-wire-hello-v1|1|{client_id}|{eph}|{time}|{nonce}"

R→C  HELLO_ACK {"v":1,"relay_id":"…","eph":"<b64 X25519 eph pub>",
                "sig":"<b64>"}
      sig = Ed25519(relay identity) над
            "poler-wire-helloack-v1|1|{relay_id}|{eph}|{hello.eph}"
      Клиент ПИНУТ публичный ключ релея (--relay-key) — MITM невозможен.
```

Обе стороны: `shared = X25519(свой_eph, чужой_eph)`; ключи направления:

```
k_c2r = HKDF-SHA256(shared; salt = SHA256("poler-wire-v1"‖hello.eph‖ack.eph),
                    info = "poler-wire/c2r")
k_r2c = HKDF-SHA256(…, info = "poler-wire/r2c")
```

AEAD ChaCha20-Poly1305: nonce12 = `00 00 00 00 ‖ seq_be64`; AAD = заголовок
(type…seq, 33 байта). Приём: `seq` строго возрастает (повтор/откат = отброс).

## 4. Агентские конверты (E2E, сквозь слепой релей)

Для агентов с криптоспособностями (`poler_agent.py`) релей не видит НИ слова:
запрос запечатан **для X25519-static клиента**, ответ — **для эфемерного ключа
агента**. Подписи Ed25519 связывают отправителя.

Конверт (JSON, тело HTTP или поле `blob` кадра EXEC):

```json
{
  "v": 1, "from": "glm", "cmd_id": "4839...", "nonce": "9918...",
  "time": "1769...", "eph": "<b64 X25519 eph pub отправителя>",
  "n12": "<b64 12 байт AEAD nonce>", "ct": "<b64 шифротекст+tag>",
  "sig": "<b64 Ed25519>"
}
```

Запечатывание: `shared = X25519(eph_priv, pub_получателя)`;
`key = HKDF-SHA256(shared; salt = SHA256("poler-env-v1‖{from}"), info="poler-env")`;
`ct = ChaCha20Poly1305(key, n12, msg = MCP JSON-RPC, aad = "poler-env-v1‖{from}‖{cmd_id}‖{nonce}‖{time}")`.

Подпись — над канонической строкой:

```
poler-env-v1|{v}|{from}|{cmd_id}|{nonce}|{time}|{eph}|{n12}|{ct}
```

Проверка на получателе: подпись отправителя (ключ из доверенного списка) →
расшифровка → окно времени ±300 c → replay-фильтр nonce → `cmd_id`.

Кто что знает: агенту вручают `box_pub` и `verify_key` клиента; клиенту —
`verify_key` каждого доверенного агента; релею — `verify_key` агента (маршрут
и проверка подписи над ШИФРОТЕКСТОМ — расшифровать не может) и привязку
`агент → клиент`.

## 5. Payload-протокол поверх кадров

EXEC (релей → клиент, внутри AEAD-сессии):

```json
{"mode":"plain","cmd_id":123,"blob":"<MCP JSON-RPC текст>"}
{"mode":"sealed","agent":"glm","cmd_id":123,"blob":"<конверт, §4>"}
```

RESULT (клиент → релей):

```json
{"cmd_id":123,"ok":true,"blob":"<ответ: MCP JSON или конверт-ответ>"}
{"cmd_id":123,"ok":false,"error":"…"}
```

HTTP-фасад релея для агентов:

| Запрос | Режим |
|---|---|
| `POST /mcp`, `Authorization: Bearer <token>`, JSON-тело | plain — релей видит тело (только для доверенных сетей/тестов) |
| `POST /mcp-sealed`, JSON-тело = конверт | sealed — релей слеп (владелец VPS видел исход, вы — нет) |
| `GET /health` | без авторизации: версия + список онлайн-клиентов |

Ответы: 200 (JSON), 400 (битый JSON), 401 (токен/подпись), 404, 413, 502
(клиент не подключён), 504 (таймаут exec, по умолчанию 120 c).

## 6. Идемпотентность и replay

- **Идемпотентность**: клиент кэширует `cmd_id → результат` (TTL 300 c).
  **Контракт ретрая**: тот же `cmd_id`, но НОВЫЙ `nonce` и новая подпись —
  релейный replay-фильтр пускает (nonce свежий), клиентский кэш отдаёт
  результат, НЕ исполняя повторно; ответ заново запечатывается под eph из
  повторного конверта. Точная копия перехваченного конверта (тот же nonce)
  на релее отбрасывается — replay невозможен без ключа агента.
  Plain-режим идемпотентности не имеет (релей генерирует cmd_id на каждый POST).
- **Replay-фильтр**: `nonce` + окно `time` ±300 c (LRU на окно); на client-leg
  дополнительно строгий монотонный `seq`.
- **Бэкофф-реконнект** клиента: 1→2→4→…→60 c с джиттером ±20%, бесконечно.

## 7. Чего в v1 НЕТ (осознанно)

- Forward secrecy на client-leg нет (эфемеральная сессия пересоздаётся при
  каждом реконнекте — этого достаточно); конверты sealed-агентов дают
  одноразовую секретность через эфемерный ключ агента.
- WebSocket/TLS-слоя нет: свой кадр поверх голого TCP; при жёстком DPI
  рекомендуется слушать 443 (трафик неотличим от «зашифрованного бинарного»).
- Double Ratchet — будущая версия (идея владельца), v1 фиксирует transcript.
- Квоты/rate-limit на релее: только потолки кадра/таймауты.

## 8. Совместимость с наброском владельца

| Набросок | В poler-wire v1 |
|---|---|
| `[Длина 4б][Тип 1б][ID 8б][Nonce 8б][Время 8б][Данные][Подпись 64б]` | кадр §2: то же + `seq`; подпись кадра заменена AEAD-тегом сессии (после handshake обе стороны уже аутентифицированы); Ed25519-подпись осталась в конвертах §4 |
| 0x01 navigate … 0x06 ping | типы — протокольные (HELLO/EXEC/…); браузерные команды НЕ экспортируются — ездит MCP JSON-RPC (анти-p3: контракт вместо голого CDP) |
| WebSocket | выброшен: нужен только для езды по чужому HTTP; у нас оба конца свои |
| «агент открывает WS к локальному серверу» | перевёрнуто: машина владельца сама подключается к релею (ноль входящих) |
